## The design -- a SHORT note `$W/scratch/s513g/overlay-design.md` BEFORE code
- **WHERE.**  Recommended: `PCL/Facts/<Module/Path>.pm` under a LIBRARY ROOT -- PCL's own `lib/` (so `lib/PCL/Facts/File/Path.pm` ships with every install because the installer copies `lib/`), and the same relative path under every other root the module lookup walks (the program's `-I` / `@INC` roots), first found wins.  That is the module's own name-to-path rule under a fixed prefix: a module without an overlay costs one failed stat per root and nothing else, and it is what lets the guard's FIXTURE module carry its own overlay under `Pl/t/lib/`.  The file is harmless if ever loaded through `@INC` (`package File::Path;` + declarations + `1;`).  If you choose a different place, say why in the note; NOT a new top-level directory (the installer and `PCLPaths` would both need changing).
- **WHAT a file may contain**: `package NAME;`, `sub name (PROTO);` forward declarations (NO body), literal `our @EXPORT = qw(...)` / `our @EXPORT_OK = qw(...)` / `our %EXPORT_TAGS = (...)`, comments, `1;`.  Anything else -- a sub with a body, an expression, a `use` -- is an ERROR naming the file and line (rule 12): an overlay is declarations, never code.  Every declaration GROUP carries a comment saying what the real module does and why a static parse cannot see it (the USER's readability requirement; the task has the File::Path example).
- **ONE reader, a MERGE.**  The extraction that reads the real module's source reads the overlay too, through the same code path, and merges: an overlay prototype fills an ABSENCE in the source scan; a CONFLICT (both declare the name, differently) is an ERROR naming both files; an overlay export list is UNIONED with the source scan's (Capture::Tiny's computed `keys %api` yields nothing to the scan).  Registered through the SAME positional path at the `use` statement (#2871).  No second table; `Pl::ProtoCache`'s key gains the overlay's bytes (or its absence), so a changed overlay is a changed module.
- **No VALUE changes.**  The real module still runs and installs the real sub; the overlay defines nothing at run time.  Verify with the detector: AFTER, an overlaid name is GONE from the log -- not recorded as "installed differs" (that would mean the overlay's prototype is wrong: fix the overlay).
