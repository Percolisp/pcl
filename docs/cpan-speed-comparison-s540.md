# The CPAN board timed under perl and under PCL (s540a, 2026-11-13)

The USER's question (s540, paraphrased): run the CPAN modules PCL's board uses
under perl and under PCL, compare the time file by file, find out where PCL is
slower, and make the list of things that should be faster (task #4787, the
first concrete piece of #4621).  This is a MEASUREMENT: nothing under `Pl/`,
`cl/` or `lib/` changed.  Every TIME in the tables is of main's code sha
**`381d9063`** (generation v2-13750, MAIN-READY-89); the PROFILES (section 4's
evidence) were taken on **`05806e16`** (MAIN-READY-91, main's code when they
ran), which moved no code they name.

## 0. The answer

**It is compile, not run.**  Over the 638 board files PCL runs exactly as perl
does (same plan, same ok count), perl spends **64.9 s of CPU** and PCL, on a
warm cache, **2,154 s -- 33.2x** (CPU normalised to a quiet box: the coarse pass
for every file, the precise re-timing for the 65 heaviest; raw 2,645 s against
perl's 71.0).  Of PCL's 2,154 s:

* **82 % (1,767 s) is LOADING** -- and 1,412 s of that is SBCL compiling the
  TEXT of the distribution's own modules on every run (a module under `-I` /
  `lib` is never compiled to a fasl by default), 225 s compiling the
  Test::More layer `cl/pcl-test.lisp` from source in every file that uses it;
* **10 % (224 s) is TRANSPILING** -- 203 s of it the test file's own `pl2cl`;
* **8 % (162 s) is RUNNING** -- 110 s in SBCL itself (most of it JSON-PP's
  `099_binary*` files) and 52 s in the subprocesses the programs
  start (Capture-Tiny).  The run phase is 2.5x perl's whole time.

A first run on an empty cache costs 3,221 s (+1,067 s: 1,362 module
transpiles, each a fresh `perl pl2cl`, and their fasl builds).  The two
cheapest levers are each one setting or one load path, and both are measured
(section 4, rows 1 and 2): compiling the dist's modules to fasls takes a
board file from 5.3 s to 0.7 s, and a compiled TAP layer saves 0.37-0.41 s in
every Test::More file.

## 1. How it was measured

**The instrument is `tools/board-timing.pl`** (checked in; its positive
control is `tools/t/board-timing.t`).  For every test file of the 30
distributions in `baselines/cpan-board-dists.tsv` it runs, one after the other
(`--jobs 1`):

* **perl**: `perl -I<dist>/t/lib -I<dist>/lib <file>` from the dist root,
  `PERL5LIB` = the dist's built prerequisites -- exactly the board's oracle
  run (`tools/run-dist-t.pl`);
* **PCL**: `pl2cl` of the test file, then SBCL on the emitted text -- the
  board's own two steps, same cwd, `-I`, `PERL5LIB` and timeout table.

**One deliberate difference from the board:** the board transpiles with
`pl2cl --no-cache`, which emits `(setf *pcl-skip-cache* t)`, so every module a
test uses is transpiled and compiled again for every file.  A user's run has
the module cache, so here it is ON, in a private cache directory per
distribution (`PCL_CACHE_DIR`; the saved runtime core passed explicitly):

* **cold** -- the dist's cache emptied, its files run in order: the first
  file pays every module's transpile and fasl build, the later ones reuse
  them.  "The first run of the suite on a fresh machine."
* **warm** -- the same files again: "a second run, nothing changed".  This is
  the DEFAULT of every table below.

The test file itself is transpiled and loaded as text on every run, as the
board does and as `pcl t/x.t` does on the first run of a changed file (`pcl`'s
script cache would skip both on a repeated run of an unchanged file).

**Wall** is Time::HiRes from fork to reap; **CPU** is user + sys of the whole
process tree (perl's `times` for the reaped children, 10 ms ticks).

**PCL's time is split into three phases** by a hooks fasl loaded in front of
the program (generated by the tool; nothing in `cl/`).  It wraps runtime entry
points with `sb-int:encapsulate` and keeps, per bucket, wall and CPU
EXCLUSIVE of nested buckets, written at exit:

| phase | buckets |
|---|---|
| **A transpile** | the test file's `pl2cl` (its own process); `xpile` = a module transpile (`p-transpile-file`, a `pl2cl` child); `evalx` + `xserver` = string-eval transpiles through the `pl2cl` server |
| **B load** | SBCL start (fork to the hooks' first form, ~15 ms); `modload` = a module's fasl or text load and its top-level code (`p-load-module-cached`, `p-load-extension`); `tap` = the Test::More layer (`p-ensure-test-lib`); the native compiles (`sb-c:compile-in-lexenv`) by whom they are for: `tcompile` the TAP layer, `mcompile` a module's text, `scompile` the test file's own forms, `ecompile` a string eval's code; `cfile` = a module fasl build |
| **C run** | everything else: the program, the eval'd code's run (`evalrun`), the END phase, and the subprocesses the program starts |

SBCL's children (its tree CPU minus its own at exit) are split: up to the
transpile buckets' wall to A (SBCL waits on a module's `pl2cl`), the rest to C.

**Which files are compared.** Only files where PCL ran its whole plan with no
failing row and the same ok count as perl, which ran its plan too (class `C`).
A file that stops early does less work and would read as fast.  `PE` files
(the same rows reached and passed as perl, but failing rows perl also fails, or
a shortfall at the same place) are listed separately; `S` = both skip the file;
`X` = anything else (a PCL failure, a timeout).

### 1a. CPU time is NOT load-proof on this box

The brief expected CPU time to inflate far less than wall time under load.  It
does not: this laptop has 8 cores with 2 threads each and a turbo clock, so a
busy box runs every thread slower.  The board gives a clean probe for it, because
every Test::More file compiles the SAME TAP layer (`cl/pcl-test.lisp`): the
`tcompile` bucket is a fixed workload measured inside each row.  Over all
coarse rows (`scratch/s540a/inflation.txt`):

| 1-min load at the file's start | rows | median `tcompile` CPU s | p10 | p90 |
|---|---:|---:|---:|---:|
| 0-2 | 728 | 0.368 | 0.359 | 0.391 |
| 2-4 | 586 | 0.428 | 0.386 | 0.498 |
| 4-6 | 163 | 0.500 | 0.439 | 0.583 |
| 6-8 | 98 | 0.608 | 0.482 | 0.830 |
| 8-10 | 85 | 0.764 | 0.627 | 0.939 |
| 10-12 | 43 | 0.857 | 0.689 | 0.980 |
| 12+ | 8 | 0.916 | 0.720 | 1.122 |

**The same compile costs 2.1-2.5x the CPU at load 8 and above that it costs at load < 2** (the coarse rows ran at a median 1-minute load of 2.2, p90 7.2, max 13.4).
Two consequences: (1) the coarse pass's CPU seconds are comparable across
chunks only after normalising each row by its own `tcompile` against the quiet
median (`tools/board-timing.pl --report --norm`; a row without Test::More takes
the median factor of its load bucket) -- every coarse CPU number below is
normalised that way; (2) the precise pass (an exclusive bench at load < 2,
best of 3) is the reference, and the doc says which table is which.

## 7. What the board does NOT tell

A test suite is a poor sample of a program's steady state, in four ways, and
the levers it cannot see are #4788's to find:

* **It is load-dominated.**  Most board files run for tens of milliseconds
  under perl; PCL's per-file constants (the test file's `pl2cl`, the TAP-layer
  compile, the module-under-test compile) are paid by every file and dominate
  the totals.  A long-running program pays them once.
* **The test harness is native in PCL.**  `use Test::More` is
  `cl/pcl-test.lisp`, not perl's Test::Builder, so each `ok` / `is` costs PCL
  a Lisp call where perl runs several method calls.  Files with tens of
  thousands of assertions make PCL's run phase look faster than the module's
  own code is (Text-CSV `55_combi.t`: 25,119 rows; section 6).
* **Its loops are short.**  Few board files run a hot loop for seconds, so
  steady-state costs -- string building, I/O loops, large sorts and hashes,
  OO dispatch at scale -- are under-weighted; the bench rows
  (`tools/bench-exec.pl`) and the everyday corpus measure those.
* **It never runs `pcl`'s script cache** (the board transpiles every file
  fresh) and, here, never the board's own `--no-cache` mode; a user's repeated
  run of an unchanged script skips phase A and the script's compile.
